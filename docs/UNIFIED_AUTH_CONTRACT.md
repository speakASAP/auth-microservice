## Unified Auth Contract (Entry Points, Flows, and Token Handoff)

This document defines the **canonical auth contract** between `auth-microservice` and all applications in the Statex ecosystem.

It is part of **Phase 0 / Sync A — Global Contracts & Architecture** in  
`shared/docs/ECOSYSTEM_REFACTOR_MASTER_PROMPT.md`. No application may implement or change auth integration outside this contract.

---

## 1. Entry URLs and Parameters

All applications must invoke auth via these entry points on the auth domain (production example: `https://auth.alfares.cz`).

### 1.1 Login

- **Route:** `GET /login`
- **Query parameters:**
  - `return_url` (required)
    - Absolute URL where the user should be returned after successful auth.
    - Must be on an allowlisted origin (see Redirect Allowlist below).
  - `client_id` (optional)
    - Logical application ID (e.g. `flipflop-service`, `crypto-ai-agent`).
    - Used for theming, logging, and client‑specific behavior.
  - `state` (optional but recommended)
    - Opaque value generated by the caller.
    - Returned unchanged on success; callers must validate it to prevent CSRF.

### 1.2 Register

- **Route:** `GET /register`
- **Query parameters:** same as `/login` (`return_url`, optional `client_id`, optional `state`).
- Semantics:
  - Shows a registration‑optimized view but still allows switching to login.

### 1.3 OAuth Providers

- **Route (init):** `GET /auth/oauth/:provider`
  - `:provider` in `{google, facebook, apple, github}` (others may be added later).
  - Query parameters: `return_url`, optional `client_id`, optional `state`.
- **Route (callback):** `GET /auth/oauth/callback/:provider`
  - Used only by the provider; applications never call this directly.

Applications **never** talk to OAuth providers directly; they always redirect to `/auth/oauth/:provider`.

### 1.4 Magic Link (Passwordless)

- **Route (request link):** `POST /auth/magic-link/request`
  - Body:
    - `email` (string, required)
    - `return_url` (string, required; same rules as above)
    - `client_id` (string, optional)
    - `state` (string, optional)
- **Route (verify link):** `GET /auth/magic-link/verify`
  - Query parameters:
    - `token` (required; single‑use, short‑lived)
    - `return_url` (optional override; if absent, uses the original value stored with the token)

## 2. Redirect Allowlist and Security

All flows that use `return_url` share the same rules:

- `return_url` must:
  - Be an absolute HTTPS URL.
  - Have an origin contained in a configured allowlist.
- Allowlist configuration:
  - Backed by environment (e.g. `AUTH_ALLOWED_REDIRECT_ORIGINS` as a comma‑separated list).
  - May be refined per `client_id` later, but global allowlist is mandatory.
- If `return_url` fails validation:
  - Auth must display a safe error page and **not** redirect.
  - Nothing is sent to the untrusted URL (no token, no user data).

Applications must:

- Only pass `return_url` values they control.
- Keep `state` values unguessable and validate them on return.

## 3. Token Handoff Contract

After successful authentication, auth‑microservice hands a token (or token pair) back to the caller.

### 3.1 Primary mechanism (URL fragment)

The primary, generic mechanism for SPAs and web apps is **URL fragment**:

- After success, auth redirects to:

  - `return_url#access_token=<JWT>&refresh_token=<JWT>&expires_at=<iso8601_or_timestamp>&state=<state>&auth_method=<method>`

- Notes:
  - Everything after `#` is **not** sent to the server by browsers; it is only visible to the frontend.
  - The frontend is responsible for:
    - Reading the fragment.
    - Validating `state` (if used).
    - Storing tokens securely (in memory, HTTP‑only cookies via its own backend, or other chosen pattern).

### 3.2 Optional mechanism (postMessage for popup flows)

For apps using a popup/login window:

- Auth may send a `postMessage` to the opener:

  - Target: `window.opener` or `window.parent`.
  - Message shape:

    ```ts
    interface AuthPostMessage {
      type: 'auth.statex.token';
      access_token: string;
      refresh_token?: string;
      expires_at?: string;
      state?: string;
      auth_method: 'password' | 'magic_link' | 'google' | 'facebook' | 'apple' | 'github';
      client_id?: string;
    }
    ```

- The caller must:
  - Listen for messages.
  - Validate `event.origin` against the auth origin.
  - Validate `state` if used.
  - Store the token securely.

The exact combination (fragment only vs fragment + postMessage) is implementation detail, but **at least fragment** MUST be supported for all apps.

## 4. JWT Shape and Semantics

### 4.1 Claims (minimum)

Auth‑microservice issues JWTs with at least:

- `sub` — internal user ID.
- `email` — primary email address.
- `roles` — list of role strings as per RBAC docs (e.g. `["global:superadmin", "app:flipflop:customer"]`).
- `auth_method` — one of:
  - `password`, `magic_link`, `google`, `facebook`, `apple`, `github`.
- Standard fields:
  - `iat`, `exp`, `iss`, and audience as currently used in the ecosystem.

Additional claims may be added, but these core ones must remain stable.

### 4.2 Transport

- Clients send the token using:
  - `Authorization: Bearer <access_token>`
- All backend services validate tokens using their configured `JWT_SECRET` and standard validation rules.

## 5. Application Responsibilities

Every application integrating with auth‑microservice must:

1. **Trigger auth via entry URLs**
   - Replace local login/register forms with:
     - Buttons/links redirecting to `/login` or `/register` on auth, including `return_url` and optional `client_id` and `state`.

2. **Handle token handoff**
   - On the `return_url` page:
     - Parse URL fragment for `access_token`, `refresh_token`, `expires_at`, `state`, `auth_method`.
     - Validate `state` if used.
     - Store the token and use it for API calls.

3. **Never bypass auth**
   - Do not implement direct OAuth flows with providers.
   - Do not mint or sign JWTs locally; only auth‑microservice does that.

---

## 6. Backwards Compatibility

- Existing endpoints (`POST /auth/login`, `POST /auth/register`, `POST /auth/validate`, `POST /auth/refresh`) remain supported.
- New flows (OAuth, magic link, centralized UI) are **additive** and must not silently break current consumers.

## 7. Validation Checklist for Sync A (Auth Contract)

A Validator Agent for Sync A (Auth) must check:

1. This document exists and is referenced in:
   - `auth-microservice/docs/agents/master-prompt.md`
   - All relevant application prompts (Flipflop, etc.).
2. Entry URLs and parameters are consistent with:
   - `shared/README.md` frontend auth summary.
3. Token handoff rules (fragment and optional postMessage) are clearly specified and compatible with:
   - At least one SPA scenario (e.g. Next.js / React).
4. JWT claim set is compatible with:
   - Existing RBAC docs and known consumers.
5. No conflicting auth contracts are defined elsewhere.

Only after this checklist passes can Sync A be considered satisfied for the auth side.

## 8. Internal Marketing Preferences API (Trusted Services)

These endpoints are for trusted internal services (for example `marketing-microservice`) and are additive.

- **Auth header:** `x-internal-service-token: <INTERNAL_SERVICE_TOKEN>`
- **Caller header:** `x-service-name: <trusted-service-name>`
- Optional allowlist by env: `TRUSTED_INTERNAL_SERVICES=marketing-microservice,...`

### 8.1 Get User Preferences

- `GET /auth/internal/users/:userId/preferences`

Returns:

- `id`
- `preferredChannel` (`email|telegram|whatsapp|none|null`)
- `fallbackChannels` (`string[]|null`)
- `perApplicationPreferences` (`object|null`)
- `perBrandPreferences` (`object|null`)
- `marketingConsents` (`object|null`)
- `transactionalOnly` (`boolean|null`)
- `unsubscribedAt` (`ISO|null`)
- `updatedAt` (`ISO`)

### 8.2 Update User Preferences

- `PATCH /auth/internal/users/:userId/preferences`

Body fields are optional and nullable (additive rollout):

- `preferredChannel`
- `fallbackChannels`
- `perApplicationPreferences`
- `perBrandPreferences`
- `marketingConsents`
- `transactionalOnly`
- `unsubscribedAt`

### 8.3 Unsubscribe Path

- `POST /auth/internal/users/:userId/unsubscribe`

Behavior:

- Sets `unsubscribedAt` to current ISO timestamp.
- Sets `transactionalOnly` to `true`.

---

## 9. Ownership Boundaries (Auth vs Marketing vs Leads)

- `auth-microservice` is the source of truth for registered-user preference and consent state.
- `marketing-microservice` may read/update auth-owned fields only via internal auth APIs in section 8.
- `marketing-microservice` must not directly mutate auth storage and must not own registered-user preference records.
- Lead preference/consent ownership stays in `leads-microservice`; auth does not become owner for lead records.
